# Multilingual support

Target languages: English, the major Indian languages, and Arabic for Gulf
customers.

## What is done

**Formatting is centralised.** Every number, amount and date in `src/` goes
through `src/utils/formatters.ts`. There are no remaining `toLocaleString`,
`toLocaleDateString` or `Intl.*` calls in application code.

**The i18n machinery is live.** `src/i18n/` initialises i18next, and the
Settings screen has a working Language row. English and Hindi ship today.
Hindi covers the shell, dashboard, sync, vouchers and settings; anything it is
missing falls back to English rather than showing a raw key. **The Hindi file
has not been reviewed by a native speaker** — do that before promoting it out
of beta, particularly the trade terms (नामे/जमा for debit/credit).

## Why we do not use `Intl`

Hermes on Android ships without full `Intl`. `toLocaleDateString(undefined, {
weekday: 'short' })` returns the *string* `"undefined"` rather than a weekday,
and number output varies by engine. Two screens had already worked around this
with private lookup tables before this work started.

Figures in this app get reconciled against Tally by hand, so they must render
identically on every device. `src/utils/localeFormatData.ts` therefore holds
explicit per-locale tables — month names, weekday names, grouping style,
separators, compact suffixes — and the formatters use only those.

## Rules that must not be broken

**The currency is never translated.** An amount that came from Tally as ₹50,000
stays ₹50,000 in every language. Only grouping and separators change. There is a
test for this.

**Digits stay Latin.** No Devanagari or Arabic-Indic numerals. Users read these
figures side by side with a Tally screen, and mixed numeral systems invite
transcription errors.

**Tally data is never translated.** Ledger names, item names, godown names and
voucher narrations belong to the customer's own company. The app will always be
mixed-language, and the language picker says so.

**Printed documents are pinned.** Invoices and vouchers format through
`DOCUMENT_LOCALE`, not the UI language: an invoice's number format is a property
of the invoice, not of whatever language the app happens to be showing.

**Statutory terms stay as they are.** GSTIN, HSN, CGST/SGST/IGST are legal
identifiers, not UI copy.

## Plural keys use the **v3** scheme — `key` + `key_plural`

`initI18n` sets `compatibilityJSON: 'v3'`, because i18next's v4 JSON format
needs `Intl.PluralRules` and Hermes cannot be relied on for `Intl` (see above).

That makes the plural suffixes:

```jsonc
"invoiceCount":        "{{count}} invoice",   // singular
"invoiceCount_plural": "{{count}} invoices"   // plural
```

**Not** `_one` / `_other` — those are the v4 format. Get it wrong and i18next
does not throw; it renders the raw key, so a user sees the literal text
`dashboard.invoiceCount` on their dashboard. That shipped once already.

`keyCoverage.test.ts` now resolves every key at both `count: 1` and `count: 5`
and fails if the result equals the key, which is the only check that catches
this. Key *existence* checks cannot — the keys were all present and correct,
just under names the configured scheme never looks for.

## Adding a language

1. Copy `locales/en.json` to `locales/<code>.json` and translate the **values**.
   Filenames are the ISO codes in `languages.ts`: `hi` Hindi, `bn` Bengali,
   `mr` Marathi, `te` Telugu, `ta` Tamil, `gu` Gujarati, `kn` Kannada,
   `ml` Malayalam, `pa` Punjabi, `or` Odia, `as` Assamese, `ur` Urdu,
   `ar` Arabic.
   - Leave `{{count}}`, `{{value}}`, `{{from}}` and friends exactly as they are.
   - Keep the `_plural` suffixes; translate both forms.
   - Do not translate `₹`, `Tally`, `GSTIN`, `HSN`, `CGST`/`SGST`/`IGST`.
2. Import it in `src/i18n/resources.ts` and add it to the `resources` map.
   (`or` and `as` are TypeScript keywords, so those two bind to spelled-out
   names — see the file.)
3. Flip `ready: true` in `src/i18n/languages.ts`, and fill in its `format`
   overrides — `months`, `monthsLong`, `weekdays`, `compactSuffixes`. Indian
   languages keep `grouping: 'indian'`; Arabic uses `'western'` because it has
   no lakh or crore.
4. Have a native speaker review it. Machine-translated accounting terms read
   badly, and "credit" / "debit" / "outstanding" have specific trade meanings.

### Topping up an existing language

`docs/i18n-missing-keys.json` lists, per language, every key English has that
that language does not — with the English text as the value. Translate the
values and merge them in.

As of the completed extraction: the 11 hand-added languages sit at **73%**
(234 keys each still to translate) and Hindi at **33%**. Everything missing
falls back to English, so a partial file is safe to ship.

`t()` calls outside React — services, class components, anything that can run
before i18n is up — use `tSafe(key, englishFallback)` instead. `realTimeManager`
and the error boundary are the examples.

Steps 2 and 3 are both required. `availableLanguages()` intersects `ready` with
the bundles actually compiled in, so flipping `ready` without registering the
file simply leaves the language out of the picker rather than offering one that
silently renders English.

## The language chip on the dashboard

`components/LanguageSwitcher.tsx` is a compact chip in the dashboard header,
next to the greeting. It is dashboard-only by construction: it lives in
`HeaderSection`, which only `PremiumDashboardScreen` renders. Every other screen
reaches the same picker through Settings → Language, so the control does not
need to follow the user around. Both entry points share
`components/settings/LanguagePickerDialog.tsx`.

### Translate the screen the navigator actually mounts

`MainNavigator` mounts the **`Premium*`** screens for all four tabs. The
similarly-named plain screens are dead code kept as fallbacks —
`DashboardScreen` is commented out in the imports, and `InventoryScreen` is
reachable only via the `InventoryList` stack route, not the Inventory tab.

An early pass translated `DashboardScreen` and got a dashboard that was still
fully English on device, because the tab renders `PremiumDashboardScreen`. Only
the figures changed language, since those come from the shared `formatters.ts`.
**Before translating any screen, check `MainNavigator.tsx` for which component
that route actually mounts.**

The live tree for the Dashboard tab is `PremiumDashboardScreen` plus
`HeaderSection`, `HeroCard`, `KpiCard`, `SalesChart`, `OutstandingList`,
`BottomNavigation`, and the `navItems` list in `data/dashboardMockData.ts`.

### Two traps this pass hit

**Never store a display string as state.** `DashboardScreen` used to keep the
billing state as `trialLabel: string | null` and then test it with
`=== 'Trial ended'` and `parseInt(label.replace(/\D/g, ''))`. Translating the
label would have silently switched off the "subscription inactive" warning. It
is now a `TrialState` union with the label derived at render. Grep for
comparisons against user-facing text before translating any screen.

**Module-scope lists cannot call a hook.** Constant arrays like `STOCK_FILTERS`
and `DEFAULT_ACTIONS` carry a `labelKey` and are translated at render, not a
`label` fixed at import time.

### Typechecking was silently dead — and now is not

This project has **no `tsconfig.json`**, so `npm test` is the only gate. Worse,
`src/services/offlineCacheService.ts` used `satisfies`, which is a TypeScript
**4.9+** keyword while `package.json` pins **4.8.4**. That made it a *parse*
error, and `tsc` skips semantic checking entirely whenever any file fails to
parse — so every type error in the project was invisible. It is now written as
a plain annotation.

With checking alive there are ~85 genuine pre-existing type errors (bad
navigation params, `Record<VoucherType, …>` maps missing four voucher types,
`unknown` assigned to typed state, a missing `inventoryService` import in
`InventoryScreen`). None are from the i18n work — they were always there. Worth
a cleanup pass of its own, and worth adding a real `tsconfig.json` so they
cannot come back.

To typecheck today, point `tsc -p` at a throwaway config with
`types: ["node"]`, `typeRoots` at `mobile/node_modules/@types`, and
`__tests__` excluded (`@types/jest` is not installed). Ignore the `TS2786`
`'Text' cannot be used as a JSX component` flood — that is the usual
`@types/react` 18 `ReactNode` mismatch, not a real defect.

### The guard tests

`src/i18n/__tests__/keyCoverage.test.ts` is what keeps the remaining work
honest:

- Every literal `t('…')` in `src/` must resolve in en.json. A typo'd key does
  not throw — i18next renders the key itself, so `settings.biomteric.title`
  would ship to a user as that exact text. Only this test catches it.
- en.json may not define a key nothing uses, so the catalogue cannot rot.
  Keys reached only through a computed lookup are listed in `computedPrefixes`.

`i18n.test.ts` additionally asserts no translation file defines a key English
lacks. Partial coverage is fine — orphans are not.

**RTL, for Arabic and Urdu.** Both are catalogued with `rtl: true`, but neither
is `ready`, and nothing calls `I18nManager.forceRTL` yet. Turning RTL on
requires an app restart to take effect and will surface layout bugs on every
screen — treat it as its own project, not as part of adding the strings.

## Note on the language switch

`src/App.tsx` keys the navigator on the active language. Translated strings
re-render on their own through react-i18next, but figures do not — the
formatters are plain function calls that react-i18next knows nothing about, so a
memoised screen would keep showing amounts grouped in the old language.
Remounting is what guarantees every figure is rebuilt; the cost is that the user
returns to the initial route after switching.
